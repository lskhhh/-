# SQL 多表连接与聚合进阶（今日汇总）

> 核心重点：连接选择、分组统计、条件计数、窗口函数、高频坑点
> 适用：SQL 简单查询、分组聚合、多表连接

---

## 一、基础聚合函数回顾

### 概念（是什么）
聚合函数对一组数据做统计，返回**单个值**。

### 语法/用法（怎么写）

| 函数 | 作用 | 关键注意 |
|---|---|---|
| `COUNT(列名)` | 统计该列**不为 NULL** 的行数 | NULL 不计入 |
| `COUNT(*)` | 统计行数 | 哪怕整行 NULL 也计数 |
| `SUM()` | 求和 | ⚠️ 没有匹配行时返回 **NULL**（重点坑） |
| `MIN()` / `MAX()` | 取最小 / 最大值 | |
| `ROUND(数值, n)` | 四舍五入，保留 n 位小数 | |
| `IFNULL(表达式, 替补值)` | 表达式为 NULL 时替换成替补值 | |
| `IF(条件, 值1, 值2)` | 条件成立返回值1，否则返回值2 | |

### 易错点（我卡在哪）
- ⚠️ `COUNT(字段)` 和 `COUNT(*)` **有区别**：前者忽略 NULL，后者数所有行。
- ⚠️ `SUM()` 在没有匹配行时返回 **NULL**，不是 0。

## 🔥 重点：条件计数三种写法

### 概念（是什么）
目标：统计满足 `result='right'` 的记录数量。

### 写法 1（最常用，SUM + IF）
```sql
SUM(IF(q.result='right', 1, 0))
```
- 逻辑：每行满足条件返回 1，不满足返回 0；`SUM` 累加求和。
- 风险：一组完全没有数据时，`SUM` 结果是 NULL，外面需要 `IFNULL` 处理。

### 写法 2（SUM + CASE，等价，可读性更强）
```sql
SUM(CASE WHEN q.result='right' THEN 1 ELSE 0 END)
```

### 写法 3（COUNT + IF）
```sql
COUNT(IF(q.result='right', 1, NULL))
```
- 逻辑：满足条件返回 1，不满足返回 NULL；`COUNT` 自动忽略 NULL。
- 优势：`COUNT` 结果**永远是数字**，不会返回 NULL，**不需要 `IFNULL` 包裹**。

### 易错点（我卡在哪）
- 三种写法都能统计"满足条件的数量"，区别在"无数据时返回 NULL 还是 0"：
  - `SUM(IF(...))` → 无数据返回 NULL，要包 `IFNULL`。
  - `COUNT(IF(...))` → 无数据返回 0，不用包。

## 正确率公式：两层 IF 区分（极易混淆）

### 概念（是什么）
正确率 = 答对数量 / 总数量，公式里会出现**两个 IF，作用完全不同**。

```sql
-- 内层IF：给 SUM 用，区分答对/答错，统计"答对数量"（统计逻辑，基本都要写）
SUM(IF(q.result='right', 1, 0))

-- 外层IF：除法保护，判断分母是否为 0，防止除 0 报错（只有分母可能为 0 才加）
IF(COUNT(q.question_id)=0, 0, 被除数 / 分母)
```

### 例子（跑过的代码）
完整带保护的正确率：
```sql
ROUND(
    IF(COUNT(q.question_id)=0, 0, SUM(IF(q.result='right',1,0)) / COUNT(q.question_id)),
    4
) AS correct_rate
```

### 易错点（我卡在哪）
| 连接方式 | 分母是否可能为 0 | 外层 IF 是否要加 |
|---|---|---|
| `INNER JOIN` | 一定有答题记录，分母不会为 0 | **可省略**，内层 IF 保留 |
| `LEFT JOIN` | 可能整组无答题，分母 = 0 | **必须加**外层 IF 防护 |

## 二、窗口函数 ROW_NUMBER()

### 概念（是什么）
- 给每行在"组内"按顺序编号，**不会合并行**，保留原始所有行。
- `PARTITION BY`：分区（类似 `GROUP BY`，但保留明细）。
- `ORDER BY`：组内排序，然后编号。

### 语法/用法（怎么写）
```sql
ROW_NUMBER() OVER(PARTITION BY 分组字段 ORDER BY 排序字段 ASC/DESC) AS rn
```

### 三种排名函数对比
| 函数 | 编号效果 | 说明 |
|---|---|---|
| `ROW_NUMBER()` | 1,2,3 | 并列强行不同号 |
| `RANK()` | 1,1,3 | 并列同号，跳过序号 |
| `DENSE_RANK()` | 1,1,2 | 并列同号，不跳序号 |

✅ 适用场景：分组后取每组第一条（比如每个学校 gpa 最低的学生）。
对比 `GROUP BY`：`GROUP BY` 合并行，只能拿聚合结果，**拿不到原始明细 id**；窗口函数保留明细。

### 例子（跑过的代码）
每个学校 gpa 最低的同学：
```sql
SELECT device_id, university, gpa
FROM (
    SELECT *, ROW_NUMBER() OVER(PARTITION BY university ORDER BY gpa ASC) AS rn
    FROM user_profile
) t
WHERE rn = 1;
```

### 易错点（我卡在哪）
- ⚠️ MySQL 5.7 不支持窗口函数，兼容写法：
```sql
(university, gpa) IN (SELECT university, MIN(gpa) FROM user_profile GROUP BY university)
```

## 三、多表连接（重中之重，今天最大难点）

### 1. INNER JOIN 内连接

#### 概念（是什么）
- 两边表能匹配上的行才保留，匹配不到直接丢弃。
- 不会产生 NULL 行。

#### 适用场景
只关心有对应记录的数据，不需要展示空数据。
例：浙大不同难度题目的正确率——只统计存在答题记录的难度，没做题的用户不展示 → `INNER JOIN`。

### 2. LEFT JOIN 左连接

#### 概念（是什么）
- 以左表为主，左表所有行全部保留；右表匹配不到，右表字段填充 NULL。

#### 关键区分：条件写在 ON 里 vs WHERE 里（超级高频坑）
| 位置 | 作用 |
|---|---|
| `ON` 后 | 只控制右表匹配哪些数据，**不会过滤左表行** |
| `WHERE` 后 | 连接完成后再过滤，NULL 参与判断会被过滤，**左表本该保留的行直接消失** |

#### 适用场景
题目要求【全部 xx 都展示，没有数据返回 0】。
例：复旦大学每个用户，8 月没练习过的也要输出，答题数 0 → `LEFT JOIN`。

### 例子（跑过的代码）
复旦那道原题：
```sql
SELECT
    u.device_id,
    u.university,
    COUNT(q.question_id) AS question_cnt,
    IFNULL(SUM(IF(q.result = 'right',1,0)),0) AS right_question_cnt
FROM user_profile u
LEFT JOIN question_practice_detail q
    ON u.device_id = q.device_id
    AND q.date >= '2021-08-01' AND q.date <= '2021-08-31' -- 时间放 ON 里面！
WHERE u.university = '复旦大学'
GROUP BY u.device_id, u.university;
```

### 易错点（我卡在哪）
- `COUNT(q.question_id)`：右表 null 时 count 结果是 0，**不需要 IFNULL 包裹**。
- `SUM(IF(...))`：完全没有匹配记录时 SUM 返回 NULL，**必须 IFNULL 转 0**，否则出现 null。

### 3. 判断口诀（刷题直接套用）
- 题目说「每个 XX，就算没有数据也要输出，结果填 0」→ `LEFT JOIN`
- 题目说「统计分类/标签（难度、题型）的数据，只关心有记录的」→ `INNER JOIN`

## 四、两道经典例题对比（极易混淆）

### 例题 A：复旦大学用户 8 月答题统计（要保留不做题用户）
- 需求：复旦所有用户都出现在结果，8 月没做题 → 答题数 = 0
- ✅ 连接：`LEFT JOIN`
- ✅ 时间条件写在 `ON` 后面
- ✅ 输出：**用户维度**，一行代表一个用户

### 例题 B：浙江大学用户各难度答题正确率（只统计答题记录）
- 需求：按难度分组，计算每种难度的正确率，不需要无答题的用户
- ✅ 连接：`INNER JOIN`
- ✅ 不会产生 `difficult_level=null` 的多余行
- ✅ 输出：**难度维度**，一行代表一个难度

```sql
SELECT
    qd.difficult_level AS difficult_level,
    ROUND(SUM(IF(q.result='right',1,0)) / COUNT(q.question_id),4) AS correct_rate
FROM user_profile u
INNER JOIN question_practice_detail q ON u.device_id = q.device_id
INNER JOIN question_detail qd ON q.question_id = qd.question_id
WHERE u.university = '浙江大学'
GROUP BY qd.difficult_level
ORDER BY correct_rate ASC;
```

### 易错点（我卡在哪）
- 分母 `COUNT(q.question_id)` 可能为 0，会触发除 0 报错；本题用 `INNER JOIN` 天然规避。
- 如果浙大题强行用 `LEFT JOIN`，必须额外加两行：
  - `HAVING qd.difficult_level IS NOT NULL` 删掉 null 分组
  - 加除 0 保护 `IF(COUNT(q.question_id)=0, 0, ...)`

## 五、GROUP BY 分组规则

### 概念（是什么）
- `SELECT` 后面非聚合字段，必须写在 `GROUP BY` 里（`only_full_group_by` 模式，牛客默认开启）。
- `GROUP BY` 后面可以用别名（MySQL 支持，Oracle 不支持）。

### 分组后过滤：WHERE vs HAVING
| 关键字 | 作用 | 阶段 |
|---|---|---|
| `WHERE` | 分组**之前**过滤原始数据（过滤行） | 聚合前 |
| `HAVING` | 分组**之后**过滤聚合结果（过滤分组） | 聚合后 |

### 例子（跑过的代码）
```sql
HAVING qd.difficult_level IS NOT NULL  -- 过滤掉 null 这一组
```

## 六、高频语法错误汇总（今天踩过的坑）

1. `distinct` 不能写在字段中间：`device_id, distinct university` 非法。
2. `distinct` 只能放在 `SELECT` 最开头，作用整行去重。
3. 别名不加空格：`ascorrect_rate` → 应为 `AS correct_rate`。
4. 表别名前后不一致：定义 `qd`，查询却写 `dq`。
5. 除 0 异常：`SUM(...) / COUNT(...)`，分母可能为 0，需要外层 `IF` 保护。
6. `LEFT JOIN` 时，把右表筛选条件写到 `WHERE`，导致本该保留的行消失。
7. 忘记排序：题目明确要求升序/降序，最后要加 `ORDER BY`。
8. `GROUP BY` 后面为空，语法报错。

## 七、刷题决策流程（做题按这个顺序思考）

1. **看需求**：输出的主体是谁？是【用户】还是【分类（难度/学校）】？
2. **看是否要求**：没有数据也要展示、返回 0？
   - 是 → `LEFT JOIN`，筛选条件放 `ON`
   - 否 → `INNER JOIN`
3. **确定统计指标**：总数量？答对数量？正确率？
   - 总条数：`COUNT(非空字段)`
   - 满足条件数量：`SUM(IF())` / `SUM(CASE)` / `COUNT(IF())`
4. **分组**：`GROUP BY 分组字段`
5. **排序**：检查题目是否要求升序/降序
6. **兜底**：检查会不会出现 NULL、除 0，按需加 `IFNULL`、`IF` 保护
